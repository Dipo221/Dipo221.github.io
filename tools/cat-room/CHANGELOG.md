# 房間裡的貓 — 改動紀錄

這支只記「哪一版改了什麼、為什麼這樣改」。功能怎麼玩、設計原則、怎麼跑測試
寫在根目錄的 `README.md`。

日期是台北時間，括號裡是 commit。每一版的完整推理都在 commit 訊息裡，
要看細節用 `git show <hash>`；美術的部分還有另一層記錄——走錯的版本留在
`art/disi.py` 的註解裡，就在要改的那幾行旁邊。

舊版的圖不需要保存。`disi.py` + `pixel.py` 是決定性的，checkout 任何一個
舊 commit 再跑一次 `python pixel.py`，就會產出那一版的素材與校對圖。

## 2026-09-01 — Disi 重畫成 24×24，groom 有了自己的一排

閣樓（20×11）上線之後貓一直是 **42px**，比房間的密度小一圈，像貼上去的。
1.5 倍不是整數，放大一定糊，所以只能重畫。**是重畫不是重新設計**——
側面斜角、六個姿勢、每個三格全部沿用，多出來的像素只拿去畫原本畫不下的東西。
`groom` 順便補上自己的一排（原待辦第 2 項），sheet 從 3 欄 5 排變 **3 欄 6 排**。

**CSS 一行都沒改。** `script.js` 從 `Sprites.manifest.frameW` 寫出 `--cat-src`，
`.cat` 用 `calc(100% * var(--cat-src) / var(--room-w))`——格子換成 24，
42px 自己變成 64px。當初把尺寸藏在 manifest 後面就是為了這一天。

**檔名改成 `disi-24.png`，順手解掉快取問題。** 格子邊長寫進檔名之後，
16→24 是換檔名不是換內容，瀏覽器不可能拿舊尺寸的圖去配新的 `background-size`。
`?v=` 忘了加是錯得安靜（畫面只是有點怪），檔名不對是連載都載不到。

### 第二輪：耳朵跟口鼻，明陽退回來重修

第一版交出去被退了兩件事，兩件都是真的錯，而且**第二件是量得出來的**。

**耳朵：頭和身體照 1.5 倍放大了，耳朵沒有。** 兩耳之間的凹口從 3 變 6（2 倍）、
單耳的粉紅從 1 格變 3 格（3 倍）。明陽說的「頭頂變平的地方變多」不是感覺，
是那個 6 格凹口。做法是回頭去 git 裡量舊的 16×16，一格一格對 1.5 倍，
**主觀抱怨就變成一張表，而且只有一個維度對不上**。

改成往外斜的尖耳：凹口收回 4、單耳 5 寬、`o` 外框 + `m` 耳殼 + 一條粉紅。
四個方案（只修比例／大耳加殼／尖耳／尖耳配矮額頭）都算繪出來讓他挑，
**而且並排兩種倍率**：14 倍看得到每一格，2.65 倍才是螢幕上真正的樣子。
耳朵在放大圖上一定看得出來，讀不讀得到要看真實密度那張。他選了尖耳。

**口鼻：對稱修好了但太胖。** 最寬那兩列 6 格 / 頭內部 10 格 = 60%，
舊的 16×16 是 3/6 = 50%。往中間縮一格變成 4/10 = 40%。
副作用是奶油色的總面積從 11.8% 掉到 9.1%，**剛好跌出 `pixel.py` 的
「主色」門檻（10%）**，所以對比 lint 現在只拿 `m`／`l` 去比地板——
40.5 階的安全距離沒有動到。

### 一條放行了四處錯誤的 lint

上一輪為了擋鼻子歪掉加的 `lint_face_symmetry()`，明陽說「鼻子下方那塊淺色
**還是**不對稱」。他是對的：那條 lint 只量「有粉紅鼻子的那一列」的奶油色，
理由是胸口和腳掌也是奶油、不能一律量。但歪掉的是鼻子**下面**那兩列，
沒有粉紅，**整個口鼻的下半段從來沒被檢查過**，四個頭裡四處一路綠燈。

**根因是拿「哪一列」當範圍——那是猜的。** 改成從鼻子的粉紅出發做四連通填充，
走得到的奶油就是口鼻那一塊，範圍變成算出來的。而它成立是靠一條早就寫死的
設計規則：**奶油色斷在脖子**（接起來貓會變成一隻穿圍兜的熊）。
胸口那塊碰不到，所以不會被誤抓；哪天有人把它接起來這條 lint 就會叫，
而那件事本來就是禁止的，叫得剛好。

順手補的：`RIGID_ROWS` 的上緣從 2 改成 1。尖耳的耳尖在 y1，框從 y2 開始的話
耳尖落在框外，耳朵歪一格檢查不到——跟框下緣那排哨兵是同一種錯，發生在另一頭。

`groom` 最低那格的 `dy=4` 原本的推導也是壞的：註解寫「下巴要落下去碰到腳」，
但抬起來的腳畫在頭那一層、會跟著頭走，**`dy` 開多少下巴到腳都一樣遠**。
真正夾住它的是地板：腳底在 y17，`dy=6` 會把它送到 y23 的地板線，
抬起來的腳一落地就只是第三隻站著的腳。上限 5，剩下只有 0/2/4 是等距的三階。

## 2026-08-28 — 天空拆成自己一層，黃昏的窗變成落日

上一版把窗加大之後，**黃昏那扇灰窗變成畫面上最搶眼的錯**，所以又插一輪修它。

**它不是畫錯，是那套機制物理上做不到。** 時段只有兩層：`multiply`（只能往暗走）
和 `screen` 的發光層（只能往亮走）。天空是全房間唯一的冷色，黃昏的暖橘
`#ffc29e` 乘下去正好把它中和成灰（`s` 120,158,186 → 120,120,115）；
發光層登記的是**夜裡**的藍，黃昏開它等於在一片橘裡點一扇藍窗。
兩條路都不通，所以只能拆層——這也正是待辦第 6 項（窗外的天氣）本來就要的。

**核心觀念一句話：色片模擬的是屋子裡的光，而天空在屋外，本來就不該吃它。**
所以天空從「算出來的」改成「**指定的**」：`room.py` 加一張 `SKY_TOD`，
四個時段各登記一組天空色，`pixel.py` 算成四張疊圖蓋在兩層上面（z-index 5）。

**四張圖做成整張房間大小、只有玻璃不透明**，不是裁一塊窗出來。
這樣 CSS 就只要 `inset: 0`，跟 `::before` / `::after` 一模一樣——
**沒有任何窗的座標被抄進 CSS**，以後屋頂開天窗也自動就有。
圖 99% 透明，四張加起來 2 KB。

**做法上真正救命的一招：先讓三個時段的顏色「不變」。**
白天／清晨／夜晚那三排填的是**舊管線算出來的實際像素值**（照 multiply 的
整數 floor 跟 glow 的 `round()` 手算再驗過），所以拆完之後那三個時段
一個像素都不會變，只有黃昏是刻意改的。驗收就變成一句可證偽的話：
`room-tod.png` 跟動手前那張比，**dawn / day / night 完全相同，dusk 只有
來源 x 140–179 / y 36–83 那 1672 個天空像素不同**——那正好是玻璃扣掉窗櫺。
（跟上一版 `_window()` 先比到 bit-identical 再換掉是同一招。改動範圍縮到
一個時段，出事一眼看得出是誰。）

意外的紅利：因為那三排等於底下的像素，**它們的 1.2 秒交叉淡入完全沒有破綻**
——溶接中露出來的底圖跟疊上去的顏色是同一個。只有進出黃昏那兩次會在中點
混進約 25% 的舊灰，不到一秒，一天兩次。不值得為它加更複雜的分層。

黃昏走的是明陽挑的**落日**：上面留一條偏紫的藍（104,92,148）、
中間橘（204,126,108）、地平線的霾最亮偏金（255,198,136）。

**兩條新的 lint，各擋一種「圖出得來但畫面是壞的」**：
`SKY_TOD["day"]` 必須等於 `PALETTE`（白天沒有東西蓋在窗上，兩邊分家的話
轉場到白天會閃一下，只有動態下看得到）；四個時段的字元集必須一樣
（漏掉的那一個會變透明，露出底下吃過 multiply 的灰）。

`?v=` 從 3 個變 7 個，所以 `save_asset()` 改成存檔時比對**解碼後的像素**
（不是檔案位元組——Pillow 的 PNG 輸出不保證穩定），只印真的變了的那幾張。
跟上一版 `room-data.js` 那條同一個做法。

`build_room_tod()` 也照 CSS 的順序把天空疊上去，所以那張四格圖仍然是
真結果不是示意圖。順手補掉 `.room::after` 沒進 `data-motion="reduced"` 的舊漏。

**沒有動任何 JS**，183 條測試不變。`EMISSIVE` 也沒動——它對窗現在是多餘的，
但 M3 的檯燈要用，而且改成天空色會讓半夜的窗變成一片大白天。

## 2026-08-28 — 窗戶加大，而且改成算出來的

明陽看過閣樓 M1 之後說**方向對**，但要窗戶加大、變成長方形、往下加長並且
再寬一點點，而且**這件做完才開始加家具**。所以這一版插在 M2（重畫貓）前面。

**窗從一格一格手打改成 `_window()` 算出來的。** 這看起來違反 `room.py`
「有形狀的東西手打」那條，其實界線沒變：手打的理由是「每一格都是美術判斷」，
而窗放大之後那些判斷一個都沒變，只是要重複更多次——4×4 是 16 塊磚、256 行，
打得出來也沒有人有辦法用眼睛驗。

**換的方法是先證明它是忠實的**：讓 `_window(2, 2)` 去跟原本那四塊手打的磚
逐位元比對，四塊、64 行全部相同才動手。第一次跑差了 4 行，全在雲——
雲寬抓成玻璃的 55%，實際是 25%。**那 4 行就是這個做法的價值**：
如果直接重畫一個「差不多像」的，這種差異永遠不會被發現。

**尺寸是排出來給明陽挑的，不是描述給他聽的。** 先算了四個（2×2 現況、
3×4、4×3、3×3）擺在同一張圖上比，他要的 3×4 有兩個看得到的毛病：
窗台直接壓在踢腳板上像門、而且 3 欄在 20 欄的房間裡偏右半格（螢幕上 21px）。
修好之後再排一次（D 與 E），他挑了 E。

**修法是讓格子比畫出來的窗大**：物件佔 4×4 格，窗只畫 48×56 縮在裡面置中，
左右各留半格、底下留半格補磚。補的磚照**絕對座標**取相位，所以跟旁邊的牆
接得起來看不出縫。**這對待辦第 5 項是好事不是將就**——可點區塊本來就該比
畫出來的東西大（手機上最少 44px），現在它自動就是。

玻璃 32×32 → 48×56，面積 2.6 倍（螢幕上 85×85 → 127×148），窗格 2×2 → 2×3。

**光柱抓的是玻璃的界，不是格子的界。** `.room-beam` 上緣改成 42.5%～57.5%
（來源 x 136～184），抓成物件的 40%～60% 會讓光從磚裡射出來。

**`room-data.js` 的 `?v=` 忘了加，而且是我自己撞到的。**
圖有各自的 `?v=`，所以快取裡的舊幾何配得上新圖——**畫面看起來是對的，
只有座標默默錯掉**。所以 `write_room_data()` 改成會比對舊內容，
真的變了就印一行 `room-data.js CHANGED -> bump ?v= in index.html`。
跟 sprite sheet 那條同一個做法：會被忘記的事要有機器講話。

已知未處理（**這一版讓它變嚴重了**）：**黃昏的窗是一大片灰**。
原因沒變（暖色 multiply 中和掉冷藍的天空，發光層登記的又是夜裡的藍），
但窗大了 2.6 倍之後它從一個小瑕疵變成畫面上最搶眼的東西，看起來像壞掉。
要修得把窗拆成自己的一層，那是待辦第 6 項的工作。
（**同一天的下一版就修掉了**，見上面那則。）

## 2026-08-27 — 房間改成 20×11 的暖色閣樓（骨架）

上一版的房間做完，明陽說**不喜歡它的長相**，並且用 AI 生了一張參考圖：
暖色閣樓、紅磚牆、木地板、斜屋頂。他自己提了對的做法——**先畫骨架，物品慢慢加**。
這一版只做骨架（牆、地板、屋頂、窗、碗），家具留給後面幾版一件一件加。

那張參考圖**沒有進 repo，也沒有被描**。AI 生的「像素圖」網格是飄的、顏色上百種，
一格一格描出來反而不像像素畫。它是情緒板不是藍圖，拿的是暖色、磚、木、斜屋頂。

**投影選斜角，不是等距。** 第一輪明陽選了等距（跟參考圖一樣），看過三種並排
之後自己改成斜角。理由是參考圖的立體感來自**家具有頂面**，不是牆歪 45 度：
家具反正要重畫，斜角幾乎免費；等距要把 Disi 重畫成 3/4 的兩個朝向（約四倍半的
畫量），而且等距地板的寬永遠是高的兩倍，橫幅房間會被壓成一條斜帶子。

**16×7 → 20×11。** 多出來的四列給斜屋頂、大樑、上半牆。地板維持四列，
A4 的縱深不會被鎖死。桌機 847×466 一次看完，手機一次看到 44%（原本 35%）。

**`art/room.py` 開頭那段預言成真了：暖色地板真的會吃掉貓。**
參考圖那種蜜色木頭亮度約 130，Disi 的中間調 `#966f55` 是 117——**地板比貓還亮**，
剪影會散掉。解法是**拉開明度不是拉開色相**：地板壓到亮度 64，跟 Disi 的亮部
差 40.5 階。代價是地板不像參考圖那麼亮，這是換來的，不是畫錯。

**而且它變成守門的規則了**：`pixel.py` 新增亮度差 lint，算地板佔比 10% 以上的
顏色跟貓身上佔比 10% 以上的顏色，最近的一對低於 30 階就 fail。跟 `bondDelta >= 0`
同一個做法——會被本能反射違反的規則要有機器擋著。

**那條 lint 第一次寫錯了，錯的版本留在註解裡。** 它把描邊也算進「貓的主色」，
於是量出 10.0 判定不合格。但描邊佔了不透明像素的三分之一，而且它要的方向
**跟身體相反**——身體要跟地板拉開，描邊要比地板暗。確認是公式錯不是房間錯的
方法是拿舊的、公認沒問題的冷紫地板去跑，它只有 2.7 分。所以 `disi.py` 多了
一個 `OUTLINE` 常數把描邊標出來，另外單獨檢查「描邊要比地板暗」。

**multiply 只能往暗走，所以多了一層發光層。** 換暖底色之後**黃昏終於推得出橘色**
（TODO 第 6 項抱怨的事解決了一半，量出來的磚是 `#7c3b26`），但夜晚變難——
暖棕乘上藍會變濁，而燈被乘暗就沒有意義了。所以 `pixel.py` 從同一份磚號表
多算一張 `room-light.png`：整張黑、只有會發光的像素是亮的，用 `mix-blend-mode:
screen` 疊在色片**之上**（黑色在 screen 底下等於沒作用，所以不用去背）。
`data-tod` 只控制它的不透明度：白天 0、夜晚 1。夜裡的窗因此是房間裡最亮的東西。

`EMISSIVE` 存的是**夜晚的顏色不是白天的**——screen 只能加亮，存白天的天空色
會讓夜晚的窗變成白天的窗。

**`room-data.js` 是新的單一事實來源。** `pixel.py` 從磚號表產出格數、地板範圍、
每個物件佔哪幾格，`script.js` 和 `style.css` 都從它算。TODO 第 4 項第 1 條
（`FLOOR` 是兩個手調的數字）因此直接關掉了，而且以後每加一個家具，
它的可點區塊自動就有座標——**那正好就是第 5 項要的資料，兩件事本來就是同一份表**。

**磚號表多了「具名多格物件」。** 床是 3×2 塊磚，一格一個字元的做法會把可用字元
用光，表也會變得看不懂。`OBJECTS` 存形狀、`place` 存座標，1×1 的小東西才留在字元表。

**屋頂重畫過一次。** 第一版是 2 列屋頂配 2 格斜邊，畫出來像「有木頭天花板的
地下室」不像閣樓：斜邊太短，讀不出那是屋頂的坡。改成斜邊每邊吃掉 4 格
（第 1 列到第 4 列），大樑只跨中間 12 欄、兩端收進斜屋頂裡——樑本來就該收在
屋架上，畫成貫穿整面牆會變成貼在牆上的飾條。

**順手修掉一個地板的真錯**：第 10 列的深色板從第 4、11、17 欄跳成 4、12、18，
一片板從房間最裡面到最前面中間換了欄，等於地板是折斷的。

**拿掉了 `build_room_tod()` 對 `--room-wall` 的 MISMATCH 檢查。** 那條的用意是
「換成像素房間時牆色不准跳」，這一版牆色是**故意**要換的，留著只會擋路。

已知未處理：**黃昏的窗會變灰**。任何暖色的 multiply 都會中和掉冷藍的天空，
而 `EMISSIVE` 存的是夜晚的藍，黃昏開發光層等於在橘色房間裡放一扇藍窗。
要修得等窗戶有自己的一層——那本來就是 TODO 第 6 項的工作，寫在 `style.css` 裡了。

**貓這一版暫時是 42px**（原生密度，只是小一圈），因為她還是 16×16。
這是故意的：先讓房間上線給明陽看方向，方向錯了不會連貓的三輪美術一起賠進去。
下一版把她重畫成 24×24 補回 64px，順便把 TODO 第 2 項（`groom` 還 alias 到
`idle`）一起做掉——整張 sheet 反正要重畫，多畫一排比之後單獨開一輪便宜得多。

## 2026-08-27 22:58 — 房間變成一張像素圖 (`57f3166`)

房間本來是四個絕對定位的 CSS 方塊配漸層，貓是 16×16 的像素。兩種語言擺在
一起，貓看起來像貼在背景上，不是住在裡面。這一版把房間也變成資料算出來的
像素圖（TODO 第 3 項）。

**做法是磚組 + 磚號表，不是整張畫。** 新的 `art/room.py`：十幾塊 16×16 的磚
配一張 16×7 的字元表，分 `bg`（牆、地板，每格都要有）和 `obj`（桌子、地毯、
窗、碗，`.` 代表空）兩層。搬家具就是改那幾行字元。整張硬鋪要 28,672 個像素，
用「一格一個字元」寫不完；8-bit 主機當年也不是那樣做的。

**尺寸是算出來的，不是挑出來的。** 一開始問題被寫成「桌機要寬、手機要窄」，
看起來得二選一。明陽自己給的解法把它拆掉了：**手機可以左右滑，桌機不用滑。**
兩邊的貓因此可以一樣大——`貓的大小 = 可用高度 ÷ 列數`，跟欄數無關。
所以列數決定貓多大，欄數是自由的，選 16×7：桌機一次看完，手機一次看到約
35%，鏡頭跟著貓跑。

**地板佔 7 列裡的 4 列，第一眼會覺得太多。** 那是留給 TODO 第 4 項的——
砍成兩列比例會好看一點，但貓就只剩一條線可以走，等於把縱深先鎖死。

**日夜是一張底圖疊一層 multiply，不是四張圖。** 四張圖是四倍美術量，
而且改一塊磚要改四次。`.room::before` 那層只換一個 `--room-tint`。
四個色值是**從舊的 `--room-wall` 反推**出來的，所以牆的顏色跟改版前逐位元
相同；`pixel.py` 的 `build_room_tod()` 會把這件事驗一次，對不上就印 MISMATCH。
那層刻意疊在貓上面——環境光本來就該打到貓身上，貓不該是唯一不受光的東西。

**兩個量出來才發現的錯**：

- **貓被壓成 72×71，不是正方形。** 站台全域有 `* { box-sizing: border-box }`，
  於是 `aspect-ratio: 16/7` 是套在**邊框盒**上的，1px 的框把內容盒擠成
  1145.4×500（比例 2.291 而不是 2.2857）。`.room` 因此獨自改回
  `content-box`，旁邊留了註解說明為什麼要推翻全域規則。
- **`--chrome`（房間以外的頁面高度）本來是用加法估的，差了 36px。**
  桌機因此會捲動 36px，違反「桌機不用滑」這條前提。改成在瀏覽器裡量：
  桌機 434、手機實測 418。手機**故意只填 340**——手機本來就會捲，
  少算那 78px 的頁尾，換來貓大 11px。

**順手做掉的兩件事**（TODO 第 1 項與第 4 項的一半）：

- **餵食不再背對著碗。** `cat.facing` 以前只在移動中更新，從碗右邊走過來的
  那幾次會背對著碗低頭吃地板。現在抵達時先讀 `cat.faceAt` 轉向，才進 `eat`。
  上一版留在這裡的「已知未處理」可以撤掉了。
- **貓有 y 軸了，鏡頭會跟。** 這超出原本只做房間的範圍，但兩件都繞不開：
  滿版房間在手機上一次看不完，貓走出畫面就變成空房間；而 `approach`
  本來就是往畫面前方走，沒有 y 軸做不出來。縱向速度是橫向的一半，
  正面走看起來本來就比較慢。TODO 第 4 項因此剩下一半，那一項已經改寫。

**`justify-content` 是 `safe center` 不是 `center`。** 房間比視窗寬的時候，
一般的 `center` 會把左半邊推到捲不到的地方——那不是美觀問題，是永遠看不到。

已知未處理：那道從窗戶斜下來的光還是 CSS 的平滑斜邊，只有它不是像素的；
multiply 推不出比底色更亮更暖的顏色，所以黃昏的天空不會變橘，晨昏兩個時段
現在長得很像；手機的橫向捲軸被藏起來了，沒有東西告訴你可以滑。

## 2026-08-26 21:59 — 真的坐姿與低頭吃 (`ea6bddb`)

sit 和 eat 原本是兩個誠實的妥協：sit 是 idle 第 0 格定住不動，eat 直接
alias 到 idle，貓站在碗邊對著空氣吃。兩個妥協的理由都是「這包素材沒有那個
姿勢」——上一版素材改成自己畫的之後，理由就不成立了。

- **sit**：頭與尾巴沿用 idle，只換肩膀以下。坐姿要成立靠兩件事——背要從
  肩膀往後下斜到落地的屁股（不是站姿那種平的）、肚子底下 x5-x6 要從 y13
  挖空到底。那個凹口是坐與站在剪影上唯一的差別，填掉就變成「站著但腿被
  擦掉」的貓
- **eat**：頭與身體分成兩層，`_eat(dy)` 只移動頭，結構上不可能把身體也

  三排：兩格奶油色直向疊起來才是一條腿，只給一排會讀成一顆白點

- `sprites.js` 的 sheet 網址加 `?v=2`。**rows 一變就一定要加號碼**，

- 測試 181 → 183，新增的兩條擋「哪天有人為了省格子又把它們指回 idle」
